# Decision: UI/UX shell permission mapping (v1.0.0)

## Context
- UI spec lists module-level permissions (e.g., buying.view, selling.view), but the current canonical `PermissionId` catalog in `packages/core/src/auth/permissions.ts` only includes generic workspace/org scopes (e.g., `workspace.data.read`, `workspace.data.write`, `org.*`).
- Navigation filtering and actions in the shell must remain permission-driven and avoid hardcoding roles.

## Decision
- Sidebar visibility for workspace modules uses `workspace.data.read`.
- Actions that represent creates/updates use `workspace.data.write` (or the module’s `disabledWhenMissing` where applicable).
- Governance routes keep their existing `org.*` permissions.
- Settings (`/app/settings`) uses `org.update`.
- “Create New” menu is shown only when `workspace.data.write` is granted; org-scoped actions would reuse `org.*` if added later.

## Rationale
- Aligns with existing permission catalog without inventing new IDs.
- Keeps UI permission-driven while avoiding incorrect placeholder permission strings.

## Follow-ups
- When module-specific permissions are added to the catalog, update the navigation and action gating to use the new IDs.
- Add tests around permission-specific navigation visibility once module permissions exist.
